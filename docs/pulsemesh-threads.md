# PulseMesh Threads protocol

Status: current and normative. PulseMesh is a new protocol; this document
defines its only supported wire contract. There is no compatibility decoder.

PulseMesh Threads carries authenticated, confidential state for one moving
object to a bounded audience. Followers calculate ETAs locally against the
Rangefind route graph and live traffic state. No tracking server learns the
capability, position, watched stop, or audience.

## 1. Security goals

The protocol provides:

- capability-confidential discovery and payload encryption;
- a signing identity cryptographically separate from capability material;
- envelope admission before AEAD and signature work;
- replay, rollback, authority-generation, and observed-fork detection;
- exact graph epoch, route-plan, and validity-window binding;
- bounded memory, parsing, DHT, dial, and per-source plus host-wide work;
- selective subscriber revocation through managed capability rotation;
- follower privacy: only publishers advertise DHT provider records.

The protocol does not hide traffic volume from a global network observer, make
a copied short-lived bearer link revocable, or make a compromised publisher
truthful. Managed subscriptions solve selective future access, not erasure of
records or secrets already received.

## 2. Roles and key separation

Every thread has two independent 32-byte values:

- `threadSecret`: a bearer capability used only as HKDF input;
- `rootPublicKey`: an Ed25519 verification identity.

For a direct-authority run, the corresponding `rootSeed` signs updates. For a
recurring route, a short-lived authority key signs under a root certificate.
Publishing or logging `rootPublicKey` does not reveal discovery or content
keys. A link holder can discover, admit, and decrypt records but cannot sign.

For a freshly generated direct run:

```text
rootSeed       = random(32)
rootPublicKey  = Ed25519.Public(rootSeed)
threadSecret   = HKDF-SHA256(rootSeed,
                   info="pulsemesh/thread/capability/1", length=32)
```

The key schedule from `threadSecret` uses empty HKDF salt:

| Output | HKDF info | Bytes |
| --- | --- | ---: |
| `K_topic` | `pulsemesh/thread/topic/1` | 32 |
| `K_content` | `pulsemesh/thread/content/1` | 32 |
| `K_admission` | `pulsemesh/thread/admission/1` | 32 |

Run seeds, authority seeds, device private keys, photo keys, and thread
secrets MUST be stored as secrets and generated by a CSPRNG in production.

## 3. Discovery

For `window = floor(unixSeconds / 300)`:

```text
tag = HMAC-SHA256(K_topic,
        "pulsemesh/thread/1" || epoch32 || uint64be(window))[0..8]
topic = /rangefind/pulsemesh/1/t/<epochPrefix16hex>/<tagHex16>
rendezvous = SHA-256(UTF8(topic))
```

Hosts subscribe to the current window and its two neighbours. Tags are opaque
and unlinkable without the capability. A publisher with a reachable address
advertises the rendezvous CID. Followers look up and dial at most eight
provider results, three peers, and two addresses per peer, with deadlines and
retry suppression. Followers MUST NOT advertise provider records: DHT
participation must not publish their interest in a private thread.

Bootstrap multiaddrs are optional, bounded hints. They are never part of the
thread topic and never placed in the capability fragment by default.

PMH1 seed cards carry one to three validated, dialable multiaddrs and an
optional short label. A seed card is a location hint, not a capability or
authority. Peer ids in multiaddrs authenticate the remote transport identity.
Ticket bootstrap hints are signed inside PMK1 and encrypted inside PME1.

## 4. Follow link

The only link encoding is 78 bytes:

| Field | Encoding |
| --- | --- |
| version | u8, exactly `1` |
| flags | u8; bit 0 means delegated authority; all other bits rejected |
| threadSecret | bytes(32) |
| rootPublicKey | bytes(32) |
| epochPrefix8 | bytes(8) |
| notAfter | uint32be unix seconds |

The base64url encoding belongs in a URL fragment. Browsers do not transmit a
fragment to the page host. A link MUST be rejected for an unknown version,
unknown flag, wrong length, graph-epoch mismatch, or expired `notAfter`.

Short-lived links are bearer capabilities. Managed subscriptions in section
11 are required when selective revocation or long-lived membership matters.

## 5. PMT1 sealed record

The maximum record size is 320 bytes.

| Field | Encoding |
| --- | --- |
| magic | `PMT1` |
| epochPrefix8 | bytes(8) |
| tag | bytes(8) |
| generation | canonical varint, positive uint32 |
| seq | canonical varint, positive |
| previousHash | bytes(16) |
| ciphertextLength | canonical varint |
| ciphertext | nonce(12) || AES-256-GCM ciphertext || GCM tag(16) |
| admissionTag | bytes(16) |

`AAD` is every encoded field from magic through `previousHash`.

```text
admissionTag = HMAC-SHA256(K_admission,
  "pulsemesh/thread/admission/1" || AAD || ciphertext)[0..16]

recordHash = SHA-256(complete PMT1 bytes)[0..16]
```

AES-GCM uses `K_content`, a fresh random 96-bit nonce for every sealed body,
the PMT1 AAD, and a 128-bit tag. Random nonces are transmitted. Sequence
numbers are never used as nonces, so restart, handover, and generation reset
cannot cause deterministic nonce reuse.

The next update by one authority sets `previousHash = recordHash` of its last
update. Certificates do not advance the update chain.

## 6. PMTP update body and signature

PMTP contains the run timestamp, state, disclosure mode, travel mode, optional
matched position, speed bin, current stop, `planRef`, cumulative stop outcomes,
cumulative bounded failure reasons, optional photo accumulator, note, and a
64-byte Ed25519 signature. The maximum plaintext body is 228 bytes, including
the signature. Encoders refuse overflow and trailing or non-canonical data.

The signature is not merely over the body:

```text
signedMessage = "pulsemesh/thread/record-signature/1"
                || SHA-256(PMT1_AAD)
                || PMTP_preimage
```

This prevents a link holder from decrypting a valid signed body and
re-encrypting it under a different generation, sequence, predecessor, epoch,
or rotating tag.

Positions use graph-local `(leafCell, geomRef, ratioQ12)`. The triple
`0,0,0` means withheld; leaf zero is otherwise valid. Coarse mode withholds
position but retains stop state. Delivery outcomes are driver assertions,
never inferred from dwell.

## 7. Validation and consistency

A subscriber performs these checks in order:

1. strict PMT1 frame, canonical values, known fields, no trailing bytes, and
   size at most 320;
2. exact graph epoch prefix;
3. tag in the subscriber's current adjacent-window set;
4. constant-time `admissionTag` verification;
5. AES-GCM open with the exact AAD;
6. strict inner PMTP or PMTC decode;
7. certificate selection, generation policy, and Ed25519 verification over
   the envelope-bound signed message;
8. replay and consistency ledger;
9. timestamp freshness and link expiry;
10. graph and motion plausibility where local data permits.

An outsider without `threadSecret` is rejected before AEAD or Ed25519 work. A
link holder can pass admission and encrypt, but cannot produce a valid
signature.

Ledgers are per authority generation. Two different valid records at the same
`(generation, seq)` freeze that authority and increment `forks`. An adjacent
record whose predecessor differs from the accepted hash also freezes it.

If `seq` jumps over unavailable records, the later correctly signed cumulative
state can be accepted for availability, but the update is returned with
`chainGap: true` and `chainComplete: false`; the subscriber increments
`chainGaps` and MUST NOT claim complete history. This is an explicit weakening
of consistency, not a silent success. Complete fork consistency across
partitioned audiences requires an external witness or transparency log.

## 8. Catch-up and offline gaps

Recent sealed PMT1 bytes are cached in bounded rings. PMR1 requests contain
exactly 4, 8, or 16 `(tag, sinceGeneration, sinceSeq)` entries and are padded
and shuffled with random decoys. The cursor is lexicographic, so a sequence
reset in a newer authority generation cannot be hidden behind an older high
sequence. PMM1 replies echo entries and contain verbatim PMT1 records.
Unknown and known-empty tags both return zero records.

Relays do not need content keys, but their work is bounded by:

- maximum record and response sizes;
- an LRU cap on cached tags and a ring cap per tag;
- new-tag and record rates per source identity;
- a host-wide per-tag token bucket that source rotation cannot bypass;
- bounded source-ledger memory and TTL cleanup.

Follower DHT privacy means catch-up normally uses already connected peers or
publisher providers. Applications requiring durable offline delivery should
run a keeper or encrypted mailbox; the protocol does not pretend opportunistic
ten-minute caches are durable storage.

## 9. Recurring authority certificate (PMTC)

Recurring routes keep one `rootPublicKey` and `threadSecret` while rotating a
short-lived signing authority. `mintDayCertificate` generates a fresh random
authority seed by default. Deterministic day-key derivation is not supported.

PMTC is 157 bytes:

| Field | Encoding |
| --- | --- |
| magic | `PMTC` |
| version | u8, exactly `1` |
| rootPublicKey | bytes(32) |
| authorityPublicKey | bytes(32) |
| generation | uint32be, positive |
| serviceDay | uint32be `YYYYMMDD` |
| planRef | bytes(8) |
| notBefore | uint32be unix seconds |
| notAfter | uint32be unix seconds |
| signature | Ed25519 bytes(64) by the root |

The root signature covers every preceding PMTC byte. Subscribers require the
certificate root to match the link, the exact envelope generation to match the
certificate, a valid signature, a live window, and a window no longer than 48
hours. A higher accepted generation makes lower authorities stale. PMTC is
sealed and periodically published on the thread topic before covered updates.

Binding `planRef` in PMTC prevents a valid day authority from being reused for
a different route plan. Binding generation makes handover and rotation
monotonic and prevents an old authority from returning after replacement.

## 10. Dispatch tickets and device sealing

PMK1 version 2 contains the run plan, publishing seed, separate thread secret,
graph epoch, expiry, disclosure mode, optional bootstrap hints, and optional
PMTC. The issuer signs the entire canonical preimage. There is no decoder for
the former ticket shape.

A plaintext ticket is both a publishing capability and customer data. It MUST
NOT leave the issuing process. PME1 seals arbitrary ticket bytes once under a
random content key and wraps that key to one or more enrolled X25519 device
public keys. How a device key becomes *enrolled* is outside this section:
either the PMV1 card moves over a side channel (paste, read aloud), or the
mesh itself carries it — §16. Opening the envelope does not replace ticket signature
verification.

Route-day tickets require the exact random authority seed returned with PMTC.
The ticket issuer verifies its public key and `planRef` before sealing. A
driver never receives the route root seed.

Proof-of-delivery photos are separately sealed under a key derived from the
publishing seed and stop scope. Gossip contains only commitments and a signed
accumulator. Hosts must re-encode images and remove EXIF before sealing.

## 11. Multi-recipient assignment (PMA1 and PMQ1)

A publishing ticket MUST NOT be sealed to a pool of candidates. Every
recipient would receive the same signing seed, making concurrent publishers
valid and indistinguishable.

`issueMultiRecipientJobOffer` instead creates one signed PMA1 assignment that
contains a seedless PMJ1 offer, a claim deadline, an issuer claim public key,
a random assignment nonce, and sorted 128-bit commitments to invited X25519
device keys. PMA1 is sealed with PME1 to up to 16 enrolled candidates. It
exposes coarse job terms and plan commitments, never the run plan, customer
data, thread secret, or publishing seed.

An invited device returns PMQ1. The claim binds the PMA1 assignment id, device
public key, timestamp, and random nonce under an HMAC key obtained from
X25519 and domain-separated HKDF. The dispatcher verifies both issuer
signatures, invitation membership, device-key possession, assignment id,
deadline, and MAC.

The winner is the first valid claim accepted by a durable atomic
insert-if-absent keyed by `assignmentId`. `awardFirstJobClaim` requires that
operation as `claimOnce`; it has no unsafe default. Candidate timestamps never
establish order. After the compare-and-set succeeds, the PMK1 publishing
ticket is available only in a PME1 envelope for the winning device.

Exactly-one assignment cannot be guaranteed by disconnected peers alone: two
partitions can each believe they won. Deployments need one linearized
dispatcher store or consensus service for the small claim record. This is a
coordination requirement, not something signatures can replace.

## 12. Managed subscriptions (PMS1)

PMS1 provides selective future revocation for long-lived audiences. It is a
root-signed grant containing:

- version and delegated flag;
- positive subscription generation;
- graph epoch prefix and validity window;
- stable root verification key;
- fresh 32-byte thread secret.

The complete 154-byte grant is sealed with PME1 to enrolled subscriber device
keys. A device opens the envelope, verifies the root signature and expected
root, checks time, and rejects any generation lower than its persisted
`minimumGeneration`.

To revoke a device, issue a strictly newer generation with a fresh thread
secret and omit that device from the PME1 recipients. Authorized devices move
to new topics and keys; omitted devices retain only expired/abandoned prior
generations. The application must persist the highest accepted generation per
root. PMS1 cannot revoke bytes already received and does not claim to.

## 13. Cross-channel isolation

Thread updates MUST NOT enter PulseMesh traffic aggregates. They have one
authoritative signer, while traffic estimates require independent evidence;
mixing them would let one fleet key move public routing costs.

A publisher may separately emit ordinary anonymous traffic contributions only
when host policy permits it. Stop arrival, dwell, and departure fixes are
suppressed so a scheduled vehicle does not create false congestion. Cadence is
appropriate only for an already-public route; unpublished courier and field
service routes require the reticent contribution profile because timing
correlation otherwise reconstructs the route.

## 15. Required security tests

Implementations must cover at least:

- fixed key-schedule, tag, rendezvous, and record vectors;
- capability/public-identity separation;
- nonce uniqueness across restart and authority generations;
- admission, AEAD, inner-body, and envelope-signature tampering;
- replay, same-sequence fork, adjacent predecessor fork, and gap reporting;
- stale authority, wrong root, wrong plan, invalid certificate window;
- managed rotation, revoked recipient, rollback, expiry, and tamper cases;
- unknown flags, versions, trailing bytes, oversized lengths, and malformed
  varints;
- per-source and host-wide flood budgets plus bounded DHT dial behaviour;
- follower non-advertisement and publisher reachability gating;
- ticket sealing, wrong device, issuer signature, and secret mismatch;
- private multi-recipient offers, invitation proof, claim tampering, deadline,
  atomic single-winner award, and loser exclusion;
- lossy-gossip catch-up and dead-zone cumulative state recovery.

The repository's `test/pulsemesh*.test.js` suite is the executable
conformance surface for this implementation.

## 16. Mesh pairing (PMP1)

Enrolment today moves the device card from the phone to the console over
whatever channel is at hand — pasted text, a URL read aloud, a messaging app
that now holds a copy. The card is public material, so nothing leaks; what it
costs is the channel itself, and the channel is the wrong way round: the
console has a screen and the phone has a camera. Pairing flips the scan. The
console displays a short-lived offer, the phone scans it and answers **over
the mesh**, and the only thing that still crosses the room by hand is the
same eight-character fingerprint two people already read to each other in a
doorway. The mesh replaces the clipboard, not the judgement.

### 16.1 Offer

`PMP1` ‖ version ‖ kind=1 ‖ pairingId(16, random) ‖ pairingPub(32, X25519) ‖
epochPrefix8 ‖ varint notAfter ‖ varint labelLen ‖ label(≤32) ‖
varint addrCount(≤3) ‖ addrs(each ≤96, multiaddr).

Displayed as `wayfind://pair#<base64url>` — a QR on the console's screen.
The offer is **unsigned**, deliberately: the operator has no long-lived
identity key to sign with and must not be given one for this, and the
offer's authenticity is physical — it is on the dispatcher's own screen in
the dispatcher's own room. An offer is a location plus a public key and
grants nothing; scanning it lets a device *propose* a card, which §16.4
filters.

The pairing keypair MUST be freshly generated per offer and discarded with
it, and MUST NOT be the issuer key or any key that outlives the session.
Reuse would turn the QR into a stable identifier of the operator, and would
let yesterday's photograph open tomorrow's channel. `notAfter` is at most
`PAIR_MAX_SECONDS` from mint. The bootstrap hints carry the operator's own
seed under exactly the caps a sealed ticket's hints carry — ≤3 entries, ≤96
bytes each — and the same travel rule: your own seed's address, never one a
stranger handed you, because the offer is shown on your screen and whatever
it names is where your drivers will dial.

### 16.2 Rendezvous

tag = HKDF(pairingId ‖ pairingPub, `"wayfind-pair-v1/tag"`, 8 bytes), and the
topic is the ordinary thread-topic namespace over `epochPrefix8` — pairing
traffic is indistinguishable from thread traffic to everything that carries
it. Both parties subscribe on their own behalf: the console when it mints
the offer, the phone when it scans. Delivery is live gossip only. Pairing
messages are not PMT1 records, are not admitted to catch-up caches, and have
no catch-up: both parties are present by definition — this is a doorway
ceremony — so nothing about it needs to persist anywhere, and nothing does.

### 16.3 Reply

`PMP1` ‖ version ‖ kind=2 ‖ pairingId ‖ PME1( PMV1 card ‖ varint timestamp ‖
pop(32) ), sealed to pairingPub. The plaintext pairingId lets the console
drop foreign replies without trial decryption.

pop = HMAC‑SHA256 over (`"wayfind-pair-v1/pop"` ‖ pairingId ‖ pairingPub ‖
devicePub ‖ timestamp), keyed by HKDF(X25519(devicePriv, pairingPub),
`"wayfind-pair-v1/key"`) — the same construction PMQ1 already uses for claim
binding. The console MUST verify the MAC, that devicePub matches the card,
and that timestamp is within `PAIR_POP_SKEW` of its clock.

This is one honest upgrade over the pasted card, and only one: a reply
proves the sender **holds the private half** of the key it is offering,
which paste never proved. It does not prove the sender is the phone in
front of you. That proof does not exist in bytes; it is §16.4.

### 16.4 Confirmation stays human

The console lists every valid reply with its `fingerprint()` and MUST NOT
enrol any of them on its own. The phone shows its own fingerprint, the two
are read aloud, and the dispatcher confirms exactly one — the ceremony §10
enrolment has always ended with, unchanged. Multiple replies are the
expected consequence of a photographable offer, not an attack signal: the
mismatched ones are somebody else's phones, and refusing them is the whole
point of the ceremony. Four bytes of SHA‑256 is not a cryptographic binding
and is still not claimed to be one.

### 16.5 Ack

`PMP1` ‖ version ‖ kind=3 ‖ pairingId ‖ PME1( varint labelLen ‖ label ‖
varint enrolledAt ‖ chosenFingerprint(4) ), sealed to the enrolled devicePub,
published on the same topic, only **after** the dispatcher confirms. The
phone that finds its own fingerprint inside shows "paired"; every other
phone learns only that it was not chosen. The ack is a courtesy, not a
record — the authoritative roster lives where it always has, in the issuing
console.

### 16.6 Hygiene

A reply is at most `PAIR_MAX_REPLY_BYTES`; one reply per (pairingId,
devicePub) — later duplicates are dropped; a console shows at most
`PAIR_MAX_CANDIDATES` distinct candidates and past that MUST stop showing
new ones and tell the operator to mint a fresh offer, because a flooded
pairing is a photographed offer. At `notAfter` or on confirmation, both
sides unsubscribe and the pairing key is destroyed. Replays after expiry
have nothing to open them.

### 16.7 What this deliberately does not do

It does not bind a device card to a libp2p peerId — the standing rule, for
the standing reason: that binding would let an operator join anonymous
traffic records to a named driver, and enrolment is the tempting place to
build it by accident. The reply is a proposal, not an enrolment; no roster
exists on the mesh. And it does not replace the pasteable card: §10's side
channel remains for depots with no mesh and for anything headless.

### 16.8 Honest costs

- A passive observer sees one sealed blob on a random topic and learns that
  a pairing happened near that time — not who, not where, not which device.
  The seed relays it and learns the same nothing.
- Anyone who photographs the offer can propose a key until it expires. The
  ceremony filters them; the expiry bounds them; neither makes the
  photograph harmless, which is why `PAIR_MAX_SECONDS` is fifteen minutes
  and not a shift.
- A 2³² grind against a 4-byte fingerprint is feasible offline. An attacker
  who already knows a target device's fingerprint could mint a colliding key
  and race the reply. That exposure is exactly today's — the pasted card has
  the same fingerprint and the same ceremony — unworsened and unrepaired.
  The defences behind it are unchanged: possession at claim time, and the
  award ceremony a wrong device still cannot win.

### 16.9 Required security tests

In addition to §15: offer expiry and post-expiry replay; reply dedupe;
pop tampering (wrong pairing id, wrong device key, stale timestamp, foreign
HKDF label); envelope sealed to the wrong recipient; oversized label, name,
and reply; unknown kind, version, and trailing bytes; the candidate cap; and
that no host path enrols a card without an explicit confirmation step.
